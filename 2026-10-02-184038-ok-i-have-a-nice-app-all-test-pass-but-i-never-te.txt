  1. Removing the two lines from Cargo.toml only changes what your crate asks

     output.
  3. Deleting the commented-out block in tests.rs changes nothing at compile
     time. It only stops machete from finding the word insta in a comment.
  4. cargo machete should then exit 0.

  That leaves two separate changes in your working copy: Cargo.toml + tests.rs,
  and Cargo.lock on its own.

  Where insta comes back

  insta comes back at step 5 of the milestone, after the build tier is green.

  Why not before

  A snapshot means "this output is correct, warn me if it changes." Today the
  output has known bugs (the lib.rs and help.rs tests in the templates), so a
  snapshot taken now would lock them in as correct. The build tier finds and
  fixes those bugs first. Then the snapshot locks in a version that's known to
  work.

  How the two connect

  The build tier and the snapshots use the same list of setups:

                setups()            ← one function: largest sets + each option 
  alone
               /        \
      build tier          snapshots
    (does it work?)    (did it change?)
    cargo test, just,   insta compares the
    clippy… on disk     text to a .snap file

  The build tier checks that the output works. The snapshot then notices if it
  changes, even in ways that don't break anything. Example from the earlier
  experiment: a lint line deleted from the Cargo.toml template. It still parses
  and builds, so only a snapshot sees it.

  Concretely, in the repo

  Why only justfile

  App::new ticks exactly the names you passed, so rust.server and just are
  checked, but rust.common and rust aren't. An option only counts if its parents
  are also checked (OptId::is_active). So rust.server was silently dropped, and
  only just rendered.

  The TUI avoids this because ticking an option calls nested_check, which ticks
  its parents too. The headless path never calls it. That's why my proposal had
  "parents are pulled in" and "fail loudly instead of dropping things": without
  them, a typo-free command can still produce a repo that's missing things, with
  no error.

  The fix: in App::new, after building options, call app.nested_check(id, 
  Some(true)) for each --opt instead of matching names inline. Then, in headless
  mode, return an error if any checked option is still inactive or conflicts
  with another. With that, your command produces rust + rust.common +
  rust.server + just.

  The bug

  mark_conflicts looks at every option, ticked or not, and records a pair
  whenever that option conflicts with a ticked one. Take the command from
  before:

  --opt rust.server --opt just      → ticked: rust, rust.common, rust.server, 
  just

  rust.firmware isn't ticked, but it conflicts with the ticked rust.common. So
  the loop records (rust.firmware, rust.common), and lib.rs returns:

  conflict options detected between: rust.firmware / rust.common

  The same goes for any setup that includes rust.common, and for rust.server
  (because of rust.client_ws). Running your earlier command again should show
  it.

  The TUI is fine because it ignores the returned list. The root problem is that
  mark_conflicts now does two jobs: greying out options for the TUI, and
  finding real conflicts. The two need different filters.

  The fix I'd suggest

  1. Put mark_conflicts back as it was, a TUI-only method.
  2. Add a separate read-only method that only compares ticked options with each
     other:
  /// The first two checked options that can't take part together, if any.
  pub(crate) fn conflict(&self) -> Option<(OptId, OptId)> {
      let checked: Vec<OptId> = self.options.iter().filter(|o|
  o.checked).map(|o| o.id).collect();
      checked.iter().enumerate().find_map(|(at, &a)| {
          checked[at + 1..].iter().find(|&&b| a.conflicts_with(b)).map(|&b| (a,
  b))
      })
  }

     checks, instead of a top-level Error variant. The message then reads input:
     `rust.firmware` and `rust.common` can't be used together, and it's

     fail in generate() first with PathCollision, which would hide the real
